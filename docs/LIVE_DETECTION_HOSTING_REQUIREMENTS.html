Road Distress Detection from a Phone Camera: Server Memory Requirements

Measured on the project's own backend while running live detection. Prepared for the hosting-plan decision.
Request: host the backend on a plan with at least 2 GB of RAM. The free tier (256 MB) cannot run live detection at all, and 1 GB leaves too little safety margin for real use.

Why the server needs this much memory

The phone only captures the camera image. The AI detection (pavement cracks, potholes, road signs) runs on the server and needs two neural-network models loaded in memory at the same time, plus the PyTorch and OpenCV libraries that run them. The phone streams a frame about every 0.4 seconds, and the server analyses it and returns the detections.

How this was tested (repeatable)

  • Script: backend/scripts/memory_profile_live.py. It starts the server, signs in, opens the same authenticated live-camera connection the app uses, sends one frame every 0.4 s for 60 s, and samples the server's memory every 0.5 s.
  • Run it with: ..\.venv\Scripts\python.exe memory_profile_live.py --duration 60 (from the backend\scripts folder). Anyone can re-run it and see the same table.

Limits of this test (stated honestly)

  • Measured on a Windows laptop. A Linux container reports memory differently and may come out somewhat lower or higher, so the plan's own memory graph should be checked after deployment.
  • Frames were a synthetic road image, not live footage. Model memory does not depend on image content, but saved detection snapshots and database writes will add a little in real use.
  • One phone connection was tested. Each additional simultaneous live session adds processing load.

Cheaper options if a larger plan is refused

  • Run live detection on a college machine or laptop and host only login, projects, audits and documents on the free tier.
  • Reduce memory by switching to the smaller CPU-only PyTorch build and loading one model instead of two. This lowers the requirement but is unlikely to reach 256 MB.
